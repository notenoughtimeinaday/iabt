# Intelligent Application Building Tool (IABT) — JERICHO Studio

IABT is a standalone creation and project-operations application. JERICHO Studio turns an authenticated objective into a server-owned plan, executes supported private work, and delivers saved artifacts. The independent stack is **Render + Neon PostgreSQL + Resend + GitHub**, with private S3-compatible file storage. Base44 is not required by the standalone runtime.

This branch advances bounded autonomy and learning from recorded evidence. It does **not** certify that every product feature is complete, that generated applications work, or that the release is ready for production. See the [completion and evidence matrix](docs/AUTONOMY_V1.md), [operational guide](JERICHO_OPERATIONS.md), and [staging acceptance runbook](STANDALONE_DEPLOYMENT.md).

## Implemented behavior

- Standalone email/password accounts, verification, password recovery, sessions, policy acceptance, owner-scoped projects and private files.
- Studio conversations, persistent uploads, saved artifact manifests, expiring private downloads, and a deliverable library.
- Server-owned capability discovery and approval policy. Supported reversible internal plans with zero external provider cost can execute automatically for the requested objective; existing IABT credits may still apply.
- Signed plans bind the execution route, normalized arguments, source checksums, price and approval. Replayed requests reuse their job and reservation.
- Optional OpenAI Responses background orchestration with registered tools, model-proposed dependency graphs, durable polling and checkpointed tool results.
- Bounded retry and recovery, immutable artifact identity, storage readback checksums, and credit capture after durable delivery. Uncertain paid submissions are not silently submitted again.
- A versioned JERICHO curriculum, account-owned execution observations, structured user corrections and evidence-linked improvement proposals. These records help future work avoid repetition; they do not train model weights or edit software autonomously.
- Existing Exchange collaboration, integration records, entitlements, Stripe test/live separation, private media adapters, document exports and application/source packages. Each has separate acceptance requirements; presence in the repository is not proof of live readiness.

Paid providers, external communication, publication, destructive operations, account/security changes and other consequential actions retain their approval gates. The model cannot grant itself tools, credentials, spending authority or infrastructure access.

## Runtime architecture

| Component | Responsibility |
|---|---|
| React + Vite frontend | Studio, files, projects, account access, billing and collaboration interfaces |
| Standalone Node API | Authentication, ownership, capabilities, signed plans, approvals, learning records and private downloads |
| Background worker | Leased jobs, Responses continuations, internal generators, provider adapters and artifact verification |
| Neon/PostgreSQL repository | Users, sessions, migrations, plans, jobs, credits, incidents, lessons and audit evidence |
| Private object storage | Uploaded and generated bytes with owner-controlled signed download links |
| Resend | Verification and password-recovery email delivery |
| GitHub + Render | Reviewed source, automated verification and authorized deployments |

Core implementation lives in `server/src/`. Autonomy policy, orchestration and tools live in `server/src/autonomy/`; the teaching curriculum and evidence service live in `server/src/learning/`. Browser code talks to the IABT adapter in `src/api/`.

A stored artifact marked verified has passed the applicable integrity and format checks. That status does not establish application behavior, factual accuracy, visual quality, accessibility, customer acceptance or deployment success. Source packages are not executed on the API/worker host. Template fallbacks and incomplete orchestration remain explicitly labeled.

## Local development

Install frontend and server dependencies from their lockfiles:

```sh
npm ci
npm ci --prefix server
```

Create `.env.local` with the local API origin:

```dotenv
VITE_IABT_API_URL=http://localhost:8787
```

Run `npm run dev` for the frontend and `npm start --prefix server` for the API. Start the worker with `npm run worker --prefix server`, or enable the embedded worker for local use. See `staging.env.example` and [STANDALONE_DEPLOYMENT.md](STANDALONE_DEPLOYMENT.md) for persistent database, storage and service settings.

Production frontend builds require a valid absolute `VITE_IABT_API_URL` origin. It is compiled into the bundle; changing it requires rebuilding. Credentials belong in server secrets, never in `VITE_*` variables or frontend files. Development OTP exposure must remain disabled outside development.

## Responses orchestration

Orchestration is off by default. Enabling it requires an OpenAI key, `IABT_ENABLE_PAID_AI`, `IABT_ENABLE_ORCHESTRATION`, `IABT_ORCHESTRATION_BUDGET_ACCEPTED`, positive `IABT_OPENAI_RESPONSE_COST_CENTS` and `IABT_ORCHESTRATION_BUDGET_CENTS`, plus the user's accepted server quote for each paid workflow.

The worker limits model turns, polls, output tokens and graph attempts. Configured supplier costs are **operator estimates, not provider-enforced dollar caps**. Review actual provider pricing, account limits and usage before authorizing live calls. Paid-provider regression tests use mocked transports; they do not prove a funded account or a live provider result.

Current orchestration tools plan dependencies, inspect approved text sources, create Markdown/DOCX/PDF documents and package source files. They cannot run shell commands, execute uploaded/generated code, access arbitrary URLs, change accounts, push Git commits or deploy services. Normal attached-file requests currently use the deterministic private source-review path described in the [operational guide](JERICHO_OPERATIONS.md).

## Verification and release

```sh
npm run verify
```

This runs lint, JavaScript validation, Exchange/creation checks, standalone server tests, file workflow tests, frontend independence checks and a production build. Set `VITE_IABT_API_URL` before verification. CI uses a reserved example origin for build verification, not deployment.

PostgreSQL tests require a disposable test database and the CI database-test settings. A skipped database test is not database evidence. `npm run verify:frontend` checks the independent and temporary legacy build paths. `npm run verify:staging` performs non-mutating HTTP smoke checks; browser workflows, email delivery, backups and payments require their own acceptance evidence.

The existing independent staging endpoints are documented in [STANDALONE_DEPLOYMENT.md](STANDALONE_DEPLOYMENT.md). Render's free API with an embedded worker can suspend while idle and is not an always-on worker guarantee. Preserve the current main branch, DNS and production setup until the reviewed branch passes the complete suite and staging acceptance. Passing local tests alone does not authorize a production cutover.

The Resend HTTP 403 was traced to missing sender-domain DNS records. On 2026-09-20 the owner-approved records were saved, Resend verified the domain, and the deployed API observed acceptance of a real reset email. Inbox receipt, successful code use and sign-in still require owner verification; provider acceptance is not inbox-delivery evidence. See the dated record in [docs/AUTONOMY_V1.md](docs/AUTONOMY_V1.md).

## Billing and launch requirements

The founding catalog remains Free, Builder, Pro and Agency, with IABT credit allowances and optional credit packs. Stripe configuration uses `STRIPE_BUILDER_PRICE_ID`, `STRIPE_PRO_PRICE_ID`, `STRIPE_AGENCY_PRICE_ID`, `STRIPE_AI_CREDIT_PACK_PRICE_ID`, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` in the **standalone server environment**. `IABT_STRIPE_MODE` defaults to test. The API derives identity, prices and redirects on the server.

Do not treat code or mocked payment tests as a verified revenue flow. Before live billing, complete checkout → entitlement → delivered artifact → cancellation/refund/credit-restoration tests, confirm actual supplier costs and margin controls, and approve the production billing setup. IABT credit restoration is distinct from a cash or supplier refund. Final policies and customer-facing commercial claims need their own release review.

## Migration and legacy context

`base44/` and the isolated Base44 frontend entries preserve historical implementation and migration compatibility. The two Base44 packages remain only for the explicitly selected temporary legacy build. The standalone browser bundle does not load the Base44 SDK, platform bootstrap, analytics or MCP consent page, and the independent server does not fall back to Base44 AI.

If maintaining an existing legacy deployment during migration, select it explicitly with `VITE_IABT_BACKEND=base44` and its historical app settings. Do not use that selector to work around missing standalone configuration. Legacy social-login behavior does not establish equivalent standalone OAuth support.

Use [BASE44_IMPORT.md](BASE44_IMPORT.md) for export/import limitations and reconcile users, projects, artifacts, files, jobs and credit balances before retiring the legacy system. Preserve the immutable legacy baseline and backups. Canonical domain/DNS changes are a separate approved release step.
